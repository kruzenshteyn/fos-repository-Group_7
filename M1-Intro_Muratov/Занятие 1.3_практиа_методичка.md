**7. Краткие теоретические сведения**

**7.1. Cloud AI**

Cloud AI предполагает передачу данных на удалённый сервер или в облачную платформу, где выполняются предварительная обработка, инференс и хранение результатов.

Преимущества Cloud AI:

- доступ к мощным вычислительным ресурсам;
- возможность использовать сложные модели;
- централизованное управление;
- удобное обновление моделей;
- централизованный мониторинг;
- возможность накопления больших объёмов данных.

Ограничения:

- зависимость от Интернета;
- дополнительная сетевая задержка;
- необходимость передачи данных;
- риски нарушения приватности;
- стоимость облачной инфраструктуры;
- возможная невозможность работы при потере связи.

**7.2. Fog AI**

Fog AI предполагает выполнение модели на промежуточном вычислительном узле, расположенном в локальной сети рядом с IoT-устройствами.

Таким узлом может быть:

- Raspberry Pi;
- промышленный компьютер;
- локальный сервер;
- IoT-шлюз;
- маршрутизатор с вычислительным модулем;
- сервер предприятия.

Преимущества Fog AI:

- меньшая задержка по сравнению с Cloud AI;
- возможность обработки данных нескольких устройств;
- снижение внешнего сетевого трафика;
- возможность локального хранения данных;
- упрощение централизованного обновления моделей внутри объекта.

Ограничения:

- зависимость от локальной сети;
- необходимость обслуживания Fog-узла;
- меньшая вычислительная мощность по сравнению с облаком;
- единая точка отказа для группы устройств.

**7.3. Edge AI**

Edge AI предполагает выполнение модели непосредственно на устройстве или рядом с источником данных.

В качестве Edge-устройства могут использоваться:

- Raspberry Pi;
- ESP32;
- NVIDIA Jetson;
- Google Coral;
- промышленные контроллеры;
- мобильные устройства;
- интеллектуальные камеры;
- микроконтроллеры с TinyML.

Преимущества Edge AI:

- минимальная задержка;
- отсутствие необходимости передавать исходные данные;
- высокая автономность;
- повышение приватности;
- возможность работы без сети;
- сокращение сетевого трафика.

Ограничения:

- ограниченная память;
- ограниченная производительность;
- ограничения энергопотребления;
- необходимость использовать компактные модели;
- более сложное обновление моделей на большом числе устройств;
- необходимость аппаратно-зависимой оптимизации.

**7.4. Сравнение архитектур**

  ----------------------------------------------------------------------------------------------
  Параметр                        Cloud AI              Fog AI                 Edge AI
  ------------------------------- --------------------- ---------------------- -----------------
  Место выполнения модели         удалённый сервер      локальный узел         само устройство

  Типичная задержка               высокая               средняя                минимальная

  Зависимость от Интернета        высокая               низкая                 отсутствует

  Зависимость от локальной сети   возможно              высокая                отсутствует

  Приватность                     ниже                  средняя                выше

  Вычислительные ресурсы          высокие               средние                ограниченные

  Централизованное обновление     удобное               удобное                сложнее

  Работа без сети                 ограничена            возможна внутри сети   возможна

  Передача исходных данных        часто требуется       не всегда              не требуется

  Типичные задачи                 обучение, аналитика   локальная агрегация    быстрое решение
  ----------------------------------------------------------------------------------------------

**7.5. Где принимать решение**

Решение следует принимать на Edge-устройстве, если:

- требуется минимальная задержка;
- система должна работать автономно;
- передаваемые данные являются чувствительными;
- сетевое соединение нестабильно;
- модель достаточно компактна.

Fog-архитектура целесообразна, если:

- необходимо обслуживать группу устройств;
- требуется локальное централизованное управление;
- Edge-устройства не обладают достаточной производительностью;
- данные не должны покидать локальную сеть.

Cloud AI следует использовать, если:

- требуется сложная модель;
- необходима централизованная аналитика;
- обрабатываются данные от большого числа объектов;
- задержка не является критической;
- имеется стабильное сетевое соединение.

На практике часто используется гибридная архитектура:

    Edge:
    быстрое локальное решение

    Fog:
    агрегация и локальный контроль

    Cloud:
    обучение, аналитика и обновление моделей

**Этап 4. Формирование статистических признаков**

**Цель этапа**

Преобразовать последовательность измерений в набор признаков, пригодный для обучения компактной модели.

**Теоретическое обоснование**

Одиночное измерение вибрации обычно недостаточно для определения состояния оборудования. Поэтому сигнал разделяют на временные окна. Для каждого окна рассчитывают характеристики, описывающие форму и энергию сигнала.

**Порядок выполнения**

Создать функцию расчёта признаков:

>     import numpy as np
>
>
>     def calculate_features(values: np.ndarray) -> dict:
>         differences = np.diff(values)
>
>         return {
>             "mean": float(np.mean(values)),
>             "std": float(np.std(values)),
>             "minimum": float(np.min(values)),
>             "maximum": float(np.max(values)),
>             "range": float(
>                 np.max(values) - np.min(values)
>             ),
>             "median": float(np.median(values)),
>             "energy": float(
>                 np.mean(values ** 2)
>             ),
>             "mean_abs_difference": float(
>                 np.mean(np.abs(differences))
>                 if len(differences) > 0
>                 else 0.0
>             ),
>         }

Разделить сигнал на окна:

>

>         "segment_id"

>         values = segment["value"].to_numpy(
>             dtype=float

>

**Этап 5. Формирование частотных признаков**

**Цель этапа**

Получить признаки, описывающие спектральный состав вибрационного сигнала.

**Теоретическое обоснование**

Аномалии вращающегося оборудования часто проявляются не только в росте амплитуды, но и в появлении новых частотных составляющих. Для обнаружения таких изменений применяется быстрое преобразование Фурье.

**Порядок выполнения**

Добавить функцию:

>     def calculate_frequency_features(
>         values: np.ndarray,
>         sampling_rate: float
>     ) -> dict:
>         centered = values - np.mean(values)
>
>         spectrum = np.abs(
>             np.fft.rfft(centered)
>         )
>
>         frequencies = np.fft.rfftfreq(
>             len(values),
>             d=1.0 / sampling_rate
>         )
>
>         if len(spectrum) == 0:
>             return {
>                 "dominant_frequency": 0.0,
>                 "spectral_energy": 0.0,
>             }
>
>         spectrum[0] = 0
>
>         dominant_index = np.argmax(spectrum)
>
>         return {
>             "dominant_frequency": float(
>                 frequencies[dominant_index]
>             ),
>             "spectral_energy": float(
>                 np.sum(spectrum ** 2)
>             ),
>         }

Использовать функцию при обработке окна:

>     SAMPLING_RATE = 1000.0
>
>     frequency_features = (
>         calculate_frequency_features(
>             window,
>             SAMPLING_RATE
>         )
>     )
>

>     import joblib
>     import numpy as np
>     import time
>
>     app = Flask(__name__)
>
>     model = joblib.load(
>         "iot_model.joblib"
>     )
>
>     scaler = joblib.load(
>         "scaler.joblib"
>     )
>
>
>     @app.post("/predict")
>     def predict():
>         request_start = time.perf_counter()
>
>         payload = request.get_json()
>
>         if payload is None:
>             return jsonify({
>                 "error": "JSON отсутствует"
>             }), 400
>
>         if "features" not in payload:
>             return jsonify({
>                 "error": "Поле features отсутствует"
>             }), 400
>
>         features = np.array(
>             payload["features"],
>             dtype=float
>         ).reshape(1, -1)
>
>         preprocessing_start = (
>             time.perf_counter()
>         )
>
>         features_scaled = scaler.transform(
>             features
>         )
>
>         preprocessing_end = (
>             time.perf_counter()
>         )
>
>         inference_start = time.perf_counter()
>
>         prediction = model.predict(
>             features_scaled
>         )[0]
>
>         inference_end = time.perf_counter()
>
>         request_end = time.perf_counter()
>
>         return jsonify({
>             "prediction": str(prediction),
>             "preprocessing_ms": (
>                 preprocessing_end
>                 - preprocessing_start
>             ) * 1000,
>             "inference_ms": (
>                 inference_end
>                 - inference_start
>             ) * 1000,
>             "server_total_ms": (
>                 request_end
>                 - request_start
>             ) * 1000
>         })
>
